# 数据更新设计

截至 2026-09-05，自动更新尚未启用。当前站点发布的是经过整理和复核的静态快照，浏览页面不会触发数据采集。后续建议每周更新一次，并继续保留完整团体档案；这份说明记录拟采用的策略，不代表已有可运行的周更任务。

## 自动更新与人工审核

首版拟自动更新已高置信绑定官号 UID 的粉丝数、精确或约数标记、来源和观察时间。身份冲突、字段缺失和异常变化进入复核队列，原有资料继续保留。页面应分别注明粉丝观察日期、存续状态截点和编辑复核日期。

存续状态、解散或复活、成员、风格、地域、官号改绑、头像和展示图继续人工审核。简介和显示名变化先保存为公开观察。请求失败、没有返回或长期没有新博文，都不能据此判定团体解散。

## 拟采用的运行约束

- 缓存优先，同一周期复用已完成的查询；业务响应完整归档并校验，凭据不进入归档或公开文件。
- 每轮设置预算、请求次数和返回条数上限，串行查询并节流。未启用前不安排自动付费查询。
- 登录失效、认证或服务不可用、额度不足、限流、超时或校验失败时停止，保留线上旧版。结果不确定的请求先核实，避免重复扣费。
- 新数据通过校验和所需人工复核后，再构建、发布并检查线上版本；公开仓库只接收审核后的数据与页面资产。

## 启用前仍需完成

现有采集和构建流程主要面向固定日期快照。周期化来源管理、完整失败留存、预算与节流、断点恢复、客观字段应用及发布前检查仍需补齐。完成一次受控运行后，再决定是否启用每周调度。

公开仓库目前没有采集或定时任务入口。运行 `npm test` 只会检查本地页面代码，不会刷新数据。
